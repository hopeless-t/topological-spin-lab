# VAL-003 — Numerical Trust / Multi-Oracle Verification

## Status

**SCIENTIFIC VALIDATION CONTRACT DRAFT**  
**C01 exploratory pilot: PASS**  
**Canonical promotion: NOT AUTHORIZED**

VAL-003 asks a question orthogonal to model adequacy and transport physics:

> When a numerical observable matters to a scientific claim, can the result
> survive independent arithmetic paths that expose product rounding, reduction
> order, dynamic-range limits, solver residuals, and deliberate corruption?

VAL-003 does not decide whether the physical model is adequate. It decides how
much trust may be placed in a bounded numerical result produced by that model.

## Why this lane exists

A calculation can converge with respect to lattice spacing and still contain a
floating-point, reduction-order, solver, or implementation error. Conversely,
a high-precision answer to an inadequate model remains an inadequate physical
answer.

The repository therefore separates:

```text
model adequacy       -> VAL-002 candidate lane
numerical trust      -> VAL-003
transport experiment -> EXP-004
```

These gates may inform each other but must not be collapsed into one PASS.

```text
        v                                    v

             CRT exact micro-GEMM oracle
                         |

          future native/high-precision lane
          MPFR / ExBLAS / OzBLAS candidate
```

The rule is not majority vote. Independent checks are used as falsifiers, and
promotion requires all checks relevant to the claim to survive.

## C01 mechanisms

### 1. Ozaki-Scheme-II-inspired CRT micro-oracle

The repository now contains a deliberately small exact integer matrix multiply:

```text
integer A, B
  -> modular matrix products
  -> Chinese remainder reconstruction
  -> independent unused-modulus check
```

The current primary moduli are:

```text
127, 125, 121
```

with product:

```text
P = 1,920,875
```

and an independent check modulus of `113`.

Signed reconstruction is permitted only when a conservative product bound is
strictly less than `P/2`. The routine fails closed outside that range.

This is an **Ozaki-Scheme-II-inspired correctness micro-oracle**, not a claim to
implement the full high-performance floating-point emulation algorithm from the
published Ozaki Scheme II.

### 2. Floating-point product error capture

For binary64 products, C01 uses a Dekker-style `TwoProduct` error-free
transformation:

```text
a * b = p + e
```

where `p` is the ordinary rounded product and `e` captures the product error
within the bounded regime of the pilot.

The product and error terms are then reduced with `math.fsum`.

This lightweight reference path is intentionally distinguished from native
NearSum, ExBLAS, or OzBLAS implementations.

### 3. Exact Fraction oracle

Small floating-point dot products are also evaluated by converting each input
binary64 value to its exact rational representation and performing the complete
operation using Python `Fraction`.

This is slow, but its purpose is oracle quality rather than throughput.

### 4. Numerical kittens

C01 deterministically generates cancellation-heavy vectors with broad but safe
binary exponents. Each kitten is a small adversarial problem intended to expose
lost low-order information.

The current real-dot kittens also test two metamorphic relations:

- permutation of dot-product terms;
- inverse power-of-two scaling of the two operands.

### 5. Solver post-check

For the current `10 Å / 8 xi` Wilson domain-wall lead Hamiltonian, C01 evaluates
an eigenpair produced by `numpy.linalg.eigh`, then recomputes:

```text
H psi - E psi
```

through the independent EFT reduction path.

It also recomputes `<sigma_x>` and checks global-phase invariance.

The EFT calculation is a **post-check**, not a replacement eigensolver.


## Red Team requirements

VAL-003 is incomplete unless the verification machinery itself can fail.

C01 includes:

1. CRT capacity overflow must be rejected rather than silently wrapped;
2. a deliberately corrupted reconstructed matrix must fail an independent
   unused-modulus check;
3. cancellation-heavy dot products must expose disagreement between the cheap
   path and the exact oracle;
4. metamorphic transforms must preserve the quantities they are supposed to
   preserve.

Future controls must include:

- exponent ranges close to overflow/underflow boundaries;
- subnormal inputs;
- non-finite values handled explicitly rather than accidentally;
- ill-conditioned eigenvalue clusters;
- backend/thread-count/order variation;
- deliberately perturbed eigenvectors and eigenvalues;
- native reproducible BLAS comparison.

## Promotion requirements

C01 remains exploratory. Before VAL-003 can become an authority-crossing lane:

1. reproduce the pilot on the repository's selected Python 3.12 CI environment;
2. qualify at least one native or independent high-precision backend candidate;
3. compare EFT results against that independent backend on widened Red Team
   cases;
4. define which classes of observable require which verification depth;
5. serialize backend version, rounding assumptions, and environment;
6. freeze the smallest verification set that detects the observed failure
   classes without making every routine unnecessarily expensive.

## Intended verification depth

The current candidate policy is:

```text
cheap exploration
    ordinary NumPy / SciPy

suspicious or decision-boundary case
    EFT dot / norm / residual

small critical algebra
    Fraction or CRT exact oracle

promotion / hard case
    independent native high-precision or reproducible backend
```

The expensive path is therefore sparse and targeted.

## Claim ceiling

A VAL-003 C01 PASS means only that the current bounded pilot successfully
constructed and exercised several independent numerical trust mechanisms.

It does **not** prove:

- correctness of every NumPy/SciPy operation;
- correctness of LAPACK eigensolvers;
- correct rounding for all inputs of the local EFT implementation;
- equivalence to NearSum, ExBLAS, OzBLAS, or the full Ozaki Scheme II;
- EXP-004 finite-device transport;
- correctness of the physical model;
- material-specific NdBi behavior.

Those require separate gates.
